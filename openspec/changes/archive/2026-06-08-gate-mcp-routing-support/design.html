A fifth face,
same onion.

How the MCP ingress bolts onto gate without disturbing the router, auth, or observation. One new Kind, one new face, an rmcp-owned wire — everything else is the machinery that already exists.

accent = new in this change
01
CONTEXT

Every face funnels one Inbound into one Router::handle.

Gate runs as a service-host service with four transport faces — a hook ingress (loopback HTTP via axum) and three loopback Unix-socket faces (tool, subscribe, admin) over a 4-byte length-prefix frame codec. Each builds an Inbound { kind, session, correlation, token, body } and hands it to the router, which mints a correlation id when absent and runs the global onion (Observe → Auth) around a per-Kind route.

ARCHITECTURE · BEFORE

Four faces in. One router. The agent CLI can only post hooks — it has no way to call gate-hosted tools.

03
ARCHITECTURE · AFTER

A fifth face — MCP, on rmcp — and a fifth Kind. The agent CLI now calls gate over a standard protocol. The onion is byte-for-byte unchanged.

+ Kind::Mcp

One variant. Method lives in the body, not the router.

+ route

PassThrough in v1 — real tools attach later.

+ sidecar

gate-mcp.url — no token on disk.

04
HOW SERVICES CONNECT

Discovery is push, not auto-detect. The orchestrator mints the session, reads the published endpoint, and injects endpoint + token into the CLI's MCP config. Only then does the CLI dial.

TWO AUTH POINTS

Connection admission rejects anonymous peers before the protocol loop; every routed call still passes the router's Auth global. Reject::Unauthenticated stays the single source of truth.

SECRET STAYS OFF DISK

The sidecar carries the endpoint only. The per-session token is one the orchestrator already holds — it minted the session — so endpoint discovery and secret distribution stay separate.

05
DECISIONS
D1

Build on rmcp; own only the request→Inbound bridge

The SDK owns transport, JSON-RPC framing, the initialize handshake, and version negotiation. Gate's only code is the handler that builds Inbound { kind: Mcp } and maps the Flow back.

vs hand-rolling JSON-RPC over the frame codec — rejected: that is a protocol library, not a framing tweak.

D2

One Kind::Mcp variant, not per-method

Method (tools/call, …) lives in the body; routing is by face. Method dispatch belongs to the rmcp handler above the route, keeping the router a thin kind→chain dispatcher.

vs McpCall/McpList variants — rejected: pushes protocol knowledge into the router for no routing benefit.

D3

v1 route is PassThrough

The face authenticates and normalizes; the route forwards. tools/list returns []; real dispatch attaches later by swapping PassThrough for tool-dispatch middleware.

vs blocking until tools exist — rejected: the proposal sequences routing first so tools ride a ready layer.

D4

Auth at admission and per request

The bearer token is read from transport metadata (HTTP Authorization; socket handshake), exactly as the hook face reads it. Anonymous connections are rejected before the loop; every routed call still passes the Auth global. Defense in depth, no extra contract surface.

D5

Streamable HTTP primary; Unix socket secondary

An MCP client dials a spawned stdio command or an HTTP URL — never a Unix socket — and a singleton daemon can't own one stdin/stdout per client. v1 binds loopback HTTP and publishes gate-mcp.url; the socket transport ships secondary for in-process clients.

note refines the proposal's "Unix socket primary, stdio first" ordering — see open questions.

D6

Endpoint is a sidecar, not the manifest, and carries no token

The face writes <base>/gate-mcp.url mirroring hook::write_gate_url; the service-host manifest stays { pid, version }. The per-session token is never written to disk — the orchestrator holds it and injects it with the endpoint.

D7

Config-selected binds via Gate::from_env

Transport and loopback port resolve in from_env and bind in bind_faces beside the other faces; the task joins self.tasks so existing task.abort() shutdown tears it down. One wiring site, one teardown path.

06
GOALS / NON-GOALS
GOALS
  • One MCP face on rmcp — no hand-rolled wire.
  • Kind::Mcp through the unchanged Observe → Auth onion.
  • Per-session bearer auth; loopback bind only.
  • Publish the endpoint as a base-dir sidecar.
NON-GOALS
  • Tool implementations — v1 exposes an empty set.
  • Remote transports / any non-loopback surface.
  • Multi-user auth — one subscription = one user.
  • A new endpoint schema in the manifest.
07
RISKS · MIGRATION
rmcp API drift

→ pin the minor version; confine all rmcp types to endpoint/mcp.rs. Router and Kind never name one.

two runtimes/transports

→ boundary stays "rmcp serves the protocol, gate builds the Inbound." No frame codec inside MCP.

empty toolset ≈ no-op

→ intended; tests prove a call is authed, routed as Kind::Mcp, observed once, forwarded — and an anon call rejected before routing.

binary size / cold start

→ gate rmcp features to those used (server, streamable-HTTP, IO); drop unused transports.

MIGRATION — ADDITIVE

No existing behavior changes. Kind gains a variant, build_router one route, bind_faces one task, Cargo.toml rmcp. The face binds only when config enables it, so gate runs unchanged until a session opts in. Rollback = remove the task and route entry; no persisted state, sidecar recreated each boot and removed on clean shutdown.

08
OPEN QUESTIONS
?? stdio reachability

If the target CLI only speaks stdio MCP, a thin stdio↔gate-mcp.sock bridge (the CLI spawns it; it dials the socket) is the path. Follow-up change, or does v1 HTTP cover the v1 CLI? Resolve before orchestrator injection.

?? ADR

New external dependency + new face. This change is spec-driven (no ADR artifact). Confirm whether rmcp adoption warrants a standalone ADR under docs/adr/ and its number.

?? session correlation

A streamable-HTTP connection is long-lived and multiplexes calls. Confirm the session id binds at admission (from the injected URL/header) and stamps every Inbound, so per-call observation stays session-correlated.
